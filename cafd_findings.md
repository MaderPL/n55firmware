# CAFD / Maps Partition — confirmed presence and impact

The file `maps/swfl_00000ff2.bin.129_160_006` (524 KB) is the **CAFD
(Calibration and Function Data)** partition that complements the ASW
(`swfl_00000fef`). XML metadata confirms it is for `MEVD17.2.6-N55`
(Bosch MEVD17.2.6 ECU for the BMW N55 engine), generated by Bosch
SWE-Generator 3.8.0.

## Flash mapping

From the XML (`swfl_00000ff2.xml.129_160_006`):

```
Segment 1:  file 0x00000000..0x0007FBFF  →  flash 0x80180000..0x801FFBFF
Segment 2:  file 0x0007FC00..0x0007FEFF  →  flash 0x801FFD00..0x801FFFFF
```

Segment 2 is the SWE Description Table / signature block. Segment 1 is
the actual calibration payload — maps, lookup tables, TX scheduler
data, signal configuration, etc.

## Confirmation that this is the missing piece

- **14,171 references** in the ASW disassembly (`dump.txt`) point to
  addresses in `0x8018xxxx..0x801Fxxxx` — i.e., into this CAFD region.
- The "blank flash" mystery from earlier analysis (TX scheduler table
  at `0x80043f90` pointing at `0x801c80xx = 0xff..ff`) was caused by
  the CAFD not being loaded; with CAFD, those targets have real data
  (though `0x801c8000` itself remains mostly zero — there may be still
  another partition for the 0x801c8000 range, or it's runtime-initialized).
- Calibration data is clearly present at known addresses, e.g.:
  - `0x801a77e9+` contains classic Bosch axis vectors / map values
    (decreasing 16-bit values that look like RPM thresholds)
  - `0x801a77b9` shows the index sequence `01 02 03 04 05 06 07` typical
    of a map's row index header
- `0x801835a8` has the pattern `8f 00 8f 00 00 00 ff ff b8 0b 40 1f`
  which is a canonical `(canId=0x8F, canIdMask=0x8F, padding, mask=0xFFFF,
  period=0x0BB8=3000, …)` TX/RX frame configuration block.

## What this means for the A5/A6/A7 encoder question

The per-frame bit layouts that the encoder code reads at runtime live in
this CAFD partition, in tables addressed by the runtime pointer chains
(`[a9]+0x1e0`, `[a9]+0x1e4`, `[a9]+0x210`, `[a0]-0x7e20`, etc.) that
were unresolvable during static analysis of the ASW alone.

To extract the A5/A6/A7 bit layout from this CAFD specifically, the
clearest path is:

1. Identify the COM-context structure that holds `a9 + 0x1e0..+0x214`
   for the 10 ms TX task. This pointer chain ultimately ends up in CAFD.
2. The base pointer is set up at boot by an init function we'd need to
   trace through. Likely candidates: `FUN_800ee312`, `FUN_800859f0`
   and friends — all of which load from `[a9]+offset` and publish into
   `[a0]-offset` global slots.
3. Once a CAFD address is found, the user's stated bit positions (A5:
   offset 16/28/40, A6: 12/24/36/48, A7: 12/32) should appear there as
   a static table.

## Quick wins available from this CAFD

- **Calibration maps** for engine functions (RPM thresholds, fuel maps,
  ignition maps) are now extractable — see e.g. `0x801a77a9+`.
- **Frame configuration** for at least some IDs is statically located —
  e.g., `0x801835a8` for canId `0x8F`.
- **The full CAN matrix** (TX + RX, including for our 5 IDs) is almost
  certainly stored as configuration tables in this partition; finding
  them is a matter of identifying the right base address among the
  many tables in the 512 KB payload.

## Notes for future passes

- The maps file uses *Intel byte order* (LE), confirmed by the XML
  (`SignatureByteOrder: INTEL`).
- The CAFD signature method is RSA-1024 with MD5; segment 1 (data
  payload) is signed. So this is an OEM-signed calibration.
- The SWE_TYPE_NUMBER is `FFFE000A` — useful for cross-referencing
  against BMW ISTA / NCD files for the same ECU.
